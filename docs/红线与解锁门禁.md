# 红线与解锁门禁

> 任何阶段评审都要回看本页。红线来自项目总规则与 [设计草稿 v1](./RemotePhone-设计草稿.md)，不可协商。

## 一、六条不可越过的红线

| # | 红线 | 具体约束 | 违反后果 |
|---|---|---|---|
| 1 | **先验证，再实现** | 不得从"API 存在"直接推导"普通 APK 可用"。ADB / Shizuku / Wireless Debugging / 各 OEM / VoLTE 必须**实测**。结论强制分级为：已确认 · 推断 · 假设 · 猜测 | 基于假设排期，返工 |
| 2 | **P0 生死线优先** | `CallAudioBridge` 未跑通前，不得魔改整个 RustDesk。不自己实现 SIP / GSM / VoLTE / VoIP / 虚拟手机号 | 掉进通信协议深坑 |
| 3 | **音频链路独立** | 电话音频与屏幕流解耦。拥塞时优先级：**音频 > 控制信令 > 屏幕视频**。屏幕卡顿不得连坐音频 | 体验致命，语音版卖不出去 |
| 4 | **变声不进 B 手机** | 固定音色部署在 Relay/Edge，默认原声、用户主动开启。禁止声音克隆、声纹训练、用户上传声音模型 | 法律与伦理风险 |
| 5 | **L4 排在 key 之后** | 移除登录/账号 UI 必须在 key 体系就绪之后，否则用户装完无法激活 | 装了用不了，版本作废 |
| 6 | **许可证与隐私** | RustDesk(AGPL-3.0)、CallVault/ShizuCallRecorder(GPL-3.0) 仅作**架构参考**，优先自研。通话音频默认**不保存、不上传、不训练** | 见 [许可证与合规](./许可证与合规.md) |

## 二、售卖解锁门禁（能卖哪层 = 哪层已做通）

| 阶段 | 解锁 | 前置门禁（全部满足才允许对外售卖） | 对应任务 |
|---|---|---|---|
| S1 | **控制版** | 客户端可编译可安装；控屏 / 触控 / 配对稳定；key 离线验签通过；激活全流程走通；私域分发包就绪 | A1–A8 |
| S2 | **语音版** | **P0 机型矩阵实测通过**（下行可提取 + 上行可注入，至少 1 款机型清晰可辨）；CallAudioBridge 端到端延迟达标；降级路径可用 | B1–B8 |
| S3 | **变声版** | 4 组固定音色在 Edge 落地；开关与降级策略就绪；延迟与算力成本已量化并告知用户 | C1–C7 |
| S4 | **摄像头版** | 定制 ROM 可刷机；虚拟摄像头 HAL 注入目标 App 验证通过；dual-use 受众边界已由业务侧书面确认 | D1–D5 |

> 门禁是**售卖**门槛，不是**开发**门槛。开发可以并行，售卖不行。

## 三、阶段推进纪律（来自设计草稿 §10）

- **一层做完美再进下一层**：S1 底座稳、key 鉴权稳，才进 S2。不并行赶工导致两层都半成品。
- **每层为下一层预留干净接口缝**：control / voice / voicechange / camera 一律以"可插拔模块 + 能力协商"存在（`MediaInjection` trait），即使当期不实现也留接口位。
- **权限位向前兼容**：新增能力只加 `ent` 位，不改既有位含义。
- **降级不伤主链**：P0 失败时收缩的是售卖范围，不是推翻控制层架构。

## 四、事实纪律（贯穿全程）

任何技术结论必须标注来源等级，写进 [事实分级清单](../poc/事实分级清单.md)：

| 等级 | 含义 | 能否作为设计依据 |
|---|---|---|
| 已确认 | 真机实测复现 | 可以 |
| 推断 | 有源码/文档支撑，未实测 | 需先验证 |
| 假设 | 逻辑上说得通，无证据 | 不可，必须先做 PoC |
| 猜测 | 凭经验 | 禁止进入设计 |

> 设计草稿 §4「客户端集成点」整节标注为**推断**——RustDesk 源码落点待 E02 确认，不要在未确认前写死。
